# 拾荒机技术报告

适用版本：0.7.6。本文记录实现约束与设计依据；构建和发行操作见 [开发者指南](DEVELOPMENT.md)，玩家说明见 [README](../README.md)。

## 架构与执行边界

作业仅在 master simulation 执行。模组添加独立 prefab、组件、Brain、StateGraph 和命名动作，不替换原版组件或全局动作，也不给小车增加可打开的储物容器。

| 模块 | 职责 |
| --- | --- |
| `modmain.lua` | 注册配方、配置、命名动作与扩展 API |
| `prefabs/automatic_collector.lua` | 网络实体、组件、显示状态和拾取/放置生命周期 |
| `ac_targets.lua` | 安全筛选、目标占用、产物预判与容器容量查询 |
| `ac_navigation.lua` | 工作范围内避障、路径跟随、岸边接近与卡住恢复 |
| `ac_compat.lua`、`ac_insight.lua` | 第三方植物只读产物识别、Insight 描述器及工作中心范围显示 |
| `components/ac_worker.lua` | 任务选择、接触时验证、货物合并、取消和存档 |
| `brains/ac_collectorbrain.lua` | 空闲时选择一个任务，忙碌时等待 |
| `stategraphs/SGac_collector.lua` | 面向目标、动作播放、交互时刻与退出清理 |
| `ac_sounds.lua` | 两款车的原创音效选择、滚动通道与启停提示 |
| `components/ac_upgradable.lua`、`ac_api.lua` | 升级等级与适配器注册 |

上述脚本模块路径均相对于 `scripts/`。每个任务只针对一个实体，动画接触时重新验证；不在一个动作中同时交互范围内所有目标。

拾荒机与升级套件的 `AddRecipe2` 显式分类均为 `TOOLS`（工具），不再注册科学或建筑分类；科技要求仍为 `TECH.SCIENCE_TWO`，材料与配方产物保持原值。原版注册接口自动加入 `MODS`（模组物品）入口。此前的 `SCIENCE` 不是当前 DST 的有效分类键，科学分类实际为 `PROTOTYPERS`，无效键会被原版 `AddRecipeToFilter` 静默忽略，创造模式也不会补齐分类。

`ac_navigation` 仅在服务端初始化小车且启用新版寻路时加载，碰撞掩码计算直接使用引擎提供的全局 `bit`。DST 没有可供 `require("bit")` 加载的模块；此前在 prefab 注册时错误地调用它，导致地表与洞穴分片启动失败。Lupa 的 LuaJIT 自带该模块，因此启动回归另在 Lua 5.1 和 LuaJIT 中模拟“全局可用、模块不可加载”的引擎环境。

## 升级套件与堆叠

`ac_upgrade_kit` 仅添加原版 `stackable`，保留组件默认的 `TUNING.STACK_SIZE_MEDITEM`（原版为 20）以及堆叠模组在组件初始化回调中设置的上限或无限堆叠规则，不在 prefab 中再次赋值。拆分与存档恢复继续由原版组件执行，不改变数量或存档格式。

原版 `stackable_replica` 从 `TUNING.STACK_SIZE_*` 建立有限的网络档位表；`maxsize` 属性赋值会立即调用 replica 的 `SetMaxSize`。此前套件写死 `20`，当堆叠模组将档位改为 `64` 等值时，查表返回 `nil` 并在初始化时崩溃。重新赋值为 `TUNING.STACK_SIZE_MEDITEM` 仍会覆盖组件初始化回调的设置，因此直接沿用原版组件初始化结果。此修复不替换任何全局堆叠组件或网络同步方法。

## 两款车的功能与采集开关

普通拾荒机仅拾取地面物品和运输，不执行采摘、收获、巨大作物敲击或资源适配器。`ac_worker:IsHarvestEnabled()` 结合 `_ac_mk2` 与单车 `harvest_enabled` 判断采集能力；`ac_targets.Kind` 在规划与接触复查中使用该条件，具体能力同时遵守 `pick_plants` 和 `hammer_giants` 配置。

空手右键 `AC_TOGGLE` 仅对地面采集车显示「开启采集 / 关闭采集」，调用 `SetHarvestEnabled`，不切换全部作业。关闭采集时仅取消尚未完成的采摘、收获、敲击和适配器任务，不施加目标冷却；已有拾取、装箱及装箱后的开启窗口继续完成。关闭期间仍扫描拾取与运输目标，批次计数和阶段保持原值，开启后继续。普通拾荒机不提供该右键动作，手持升级套件的 `AC_UPGRADE` 安装继续保留。

`_ac_harvest_enabled` 在 `SetPristine` 前声明，用于客户端右键提示；服务端复查目标有效、已升级及未收起。组件存档新增 `harvest_enabled`，与工作中心、货物和批次共同恢复，捡起再放置保留开关选择。旧存档缺少该字段时将旧暂停迁移为关闭采集并恢复完整作业，因此旧普通拾荒机也能继续拾取运输。升级等级与 worker 的恢复顺序不影响开关选择。原 `SetEnabled` 保留为扩展的完整启停接口，新存档仍能分别保存这两个状态。

两款车的玩家拾取仅通过鼠标左键。原版 `inventoryitem.canbepickedup=false` 经 replica 同步，原版“行动”键扫描及指定目标请求均无法生成小车的 `PICKUP`；普通掉落物继续沿用原版选择。左键专用 `AC_PICKUP` 通过组件场景动作接入，使用原版玩家短动作及拾取到达参数，服务端复查后调用原版 `inventory:GiveItem`，继续执行既有小车拾取回调并交还货物。此实现不替换原版输入函数或全局拾取动作，右键仍分别用于升级安装和采集切换。

## 音效执行边界

0.6.1 将升级版显示名改为「采集车」，保留 prefab、升级等级与存档格式。两款车使用 `sound/ac_collector.fev/.fsb` 中独立的木质/金属事件；源音频由 `tools/build_sounds.py` 原创合成，构建与验收见 [音效说明](SOUNDS.md)。

主模拟端在 StateGraph 中调用实体 SoundEmitter，客户端沿用引擎传播，不重复执行声音逻辑。作业音效只在接触时验证通过后播放一次；收获共用采摘声。行走使用命名通道 `ac_walk`，连续动画循环不重复启动，非行走状态及拾起、休眠、移除时停止并清标志。启停提示跳过背包与休眠实体。升级使用独立装配声，配方、移速与作业时长保持不变。

## 集中采集与集中运输

默认一个原版 `inventory` 运输槽，货物随原版库存存档保存。农作物分为采摘与清理两个阶段：空载时优先选择农作物，每成功采摘 5 个进入清理阶段；不足 5 个但已无可采作物也清理当前批次。清理阶段只允许巨大作物敲击、地面拾取和运输；车内货物送完且当前没有可执行的清理任务后，重置计数并恢复采摘。草、树枝、普通浆果丛等非农作物仍按原有同类产量凑组作业。

落地巨大果实的敲击优先级严格高于继续采摘巨大植株，果实散落位置不会改变此顺序：采摘巨大植株后，地面巨大果实先逐次执行一次原版工作量，完成敲开后才能继续下一株或拾取运输。第 5 个巨大植株也遵循此顺序，敲击不计入采摘数量；松果等额外掉落不会在批次未完成时触发地面拾取。

拾取数量同时受运输槽余量、物品自身堆叠上限和至少一个接收箱可容纳该组货物的容量约束。合并使用原版 `CanStackWith`，保留皮肤与第三方规则。接触时只拆取当前目标所需数量，再执行原版 `PICKUP`；例如上限 40、已携带 39、地面有 7 时，只取 1，剩余 6 留在原地。

农作物识别依据 `farm_plant`、成熟 `crop`、棱镜 `perennialcrop` / `perennialcrop2` 组件及勋章果树标签。选择与接触时不预判农作物产量，不查询样品箱或容量，只复查成熟度、可交互、安全、范围与占用；因此子圭垄非巨大作物不会因空产物字段或满箱预检而被跳过。普通采摘资源仍纯查询主产物和单次产量，不生成预览物品或调用随机回调；下一株放不下时先卸货。

农作物回调可能直接向小车原版库存发放产物。任务在创建时记录是否为农作物，结束时对实际运输槽和临时手持槽内物品逐个调用 `DropItem(item, true)`，保持原实体、数量、皮肤、潮湿与腐烂状态，不复制或删除产物；农作物产物统一落地，稍后分组拾取。部分发放后动作失败也放下已产生的真实物品，但不增加采摘计数。普通资源仅将额外产物/临时槽溢出落地，不主动扩充运输容量。不处理打蜡巨大作物或普通建筑。

## 容器与空间限制

容器必须在工作半径内、位于同一平台、具备开启能力（`canbeopened`）、非只读，并满足角色限制及原版物品过滤和 `CanAcceptCount`。接收箱是否已被玩家或其他机器打开不参与筛选，不调用 `CanOpen()` 或 `IsOpenedByOthers()` 预检；实际存放仍由原版 `STORE` 执行。默认配置为仅已有同类物品的箱子；允许空箱模式仍优先已有同类物品的接收容器。所有容器均失去实际接收能力时，在当前位置丢出整组货物，再返回工作中心。

运输中的 watchdog 每 .1 秒复查当前接收容器。容量、过滤、安全或样品条件变化时，通知原版 BufferedAction 失败监听器、清理移动与状态机，再立即重新选择容器；这类重新规划不施加 10 秒失败冷却。单纯开箱不会取消运输。若没有可接收容器，参照原版 `storage_robotbrain.lua` 的 `GoHomeAction`，在当前位置调用 `inventory:DropItem(item, true, true)` 丢出整组货物，再返回工作中心。每次只处理一组，未来多槽升级不会连带丢出其他有接收箱子的货物；地面物品只有存在接收容量时才重新拾取，避免满箱时反复捡起与丢出。接触时也复查当前目标能否接收，不因出现另一个排名更优的箱子而单独判定当前任务失败。

`unreachable`、`stuck` 与 `search_timeout` 另记入弱键 `navigation_failures`。正常目标与接收箱选择均无结果时，`FindContainer(..., allow_waiting=true)` 只额外检查处于导航冷却、且仍能真实接收当前货物的箱子；存在时保留原货物并显示“运输受阻”，待冷却结束再尝试。不会将“暂时走不到”当成“没有接收能力”，避免围墙或拥挤场景中多车轮流拾取和丢出同一批货物。若等待期间箱子满、被移除或拒收，仍执行逐组落地规则。成功及重新放置清除相应导航失败状态。

农作物采摘及巨大果实敲击无需预测接收容器。普通资源的空载预检仍对已知产物采用“任意一种匹配”规则。清理结束判定复用 `FindWork(..., "drain", entities)` 的实际可执行结果：空载且无可执行任务时结束。缺少匹配箱、满箱、过滤拒收、失败冷却及目标被其他机器占用的物品均留地跳过；恢复接收条件后仍可重新拾取。v0.5.3 允许已打开的箱子参与实际容量查询，不再因开箱跳过掉落物。能力勋章的 `medal_gift_fruit_oversized` 敲开时通过 `DropGift` 生成多种随机产物，各类产物按真实接收能力独立处理。

每次规划只做一次范围实体查询，采摘、清理与常规模式共享当前候选列表，容器查询仍缓存到本次时刻。批次计数与阶段随存档恢复；关闭采集、扩展暂停和休眠保留，拾取/重新放置重置。失败和重复回调不增加计数，旧存档缺少批次字段时从零开始。

工作中心固定在放置位置。普通拾荒机使用服务器配置的半径 8 / 12 / 16；0.6.1 采集车固定为 20（约 5 块地皮），采摘与箱子查询均使用该值。升级应用时清除同一时刻的接收箱缓存并同步 `_ac_radius`，存档按原等级重新应用，撤销等级恢复配置值，安装失败恢复原半径。拾取与敲击额外允许 2 个世界单位，覆盖掉落物散落位置。船上中心跟随平台移动，只处理同一平台，不跨船或跨海。实体休眠时取消任务，不模拟离线瞬间采集。

服务器选项 `new_navigation` 默认开启，`modmain.lua` 将缺省值归一为 `true`。两款小车在服务端初始化时按当前设置决定是否挂接 `ac_navigation`；关闭时不加载模块、不包装任何原版移动方法，使用游戏原版寻路。开关不存入单车数据，更改后重新载入世界即可作用于已有小车；目标筛选范围、车身尺寸与工作组件保持原规则。以下路径算法说明对应开启状态。

`ac_navigation.lua` 只接管该小车实例的 `locomotor.FindPath`、`OnUpdate`、`Stop`、`Clear`、`WantsToMoveForward`、`SetMoveDir` 与 `SetMotorSpeed`，不替换原版全局组件。范围内直达路线优先；需要绕行时使用以 .75 单位粗网格为主、局部 .25 单位细化的 A* 和二叉堆，单次最多展开 4096 个节点。每条边先检查范围和快照中的实体碰撞，再检查原版 `Pathfinder:IsClear`、地图通行与车身左右净空；最终交互接近也先排除实体阻挡，再采样地形。实体障碍按双方真实 Physics 碰撞组、掩码、激活状态与半径筛选，以车身半径加 .05 单位余量膨胀。雕像、树木、墙、箱子、玩家与生物参与行车避障；其他 `automatic_collector` 不进入规划障碍列表，拥挤由原版角色碰撞和卡住退避处理，不关闭车身碰撞。不阻挡车身的掉落物和禁用碰撞的实体不占路。搜索停在原版动作到达距离内的可接近位置，不要求走进箱子的碰撞体。节点限制以工作中心为圆心，存放、采摘和返程使用工作半径，拾取/敲巨果沿用额外 2 单位容差；从容差边缘或旧存档圈外出发时，仅允许不超过出发距离的路线，避免无法返程。

搜索使用按世界隔离的协程队列，同一模拟帧共享 128 个工作单位，每轮最多使用 16 个单位后移到队尾。快照启动、A* 节点展开、额外细网格邻居批次和平滑候选各按整单位计费；实体过滤、索引桶访问、候选碰撞检测、地形查询和间隙点构建等内层操作各计 1/128 单位，允许在循环中让出。初始、完成及途中复查的异步快照合计每帧最多启动 4 次实体查询，结果处理与建索引继续分片。单次引擎 `FindEntities` / `Pathfinder:IsClear` 调用不可拆分，预算单位不是固定执行时间或实机帧率保证。等待期间保留目标与动作，停止马达并向状态机报告暂不前进，动画重新设速也不能恢复移动。相同目标不重复排队，取消、收起和目标失效后旧搜索不能恢复任务。完成搜索后先按最新障碍及目标位置验证，再恢复行走。

碰撞快照使用 2 单位空间哈希：每个碰撞体按膨胀半径的包围盒写入覆盖的格子，线段按 DDA 遍历经过的格子，去重候选后再作精确圆形检测，避免每条边全量遍历范围内实体。跨多个格子的大碰撞体仍参与检测。船上的索引与障碍位置保存在平台局部坐标中，无需在每帧转换整份障碍列表；工作中心在快照构建开始时也捕获局部坐标，防止构建跨帧时船体移动造成中心偏移。初始 Context 创建时即登记到任务状态，平台移除或变更后不会继续恢复旧平台的构建。

窄路在同一搜索中局部细化：网格节点以起点为原点、.25 单位为整数索引，开阔处仅连接 .75 单位粗网格点。范围内的粗连接被障碍或地形拒绝时，扩展 .25 单位八邻居；纯地形窄道也能触发，单纯超出工作圆的候选不触发沿圆周密集细化。细节点同时尝试邻近粗网格，粗连接均可通行时不再扩散细节点。相邻静态圆形碰撞体膨胀后仍有不超过 .75 单位的空隙时，另在自由区间中点生成几何节点，并排除被第三方碰撞体、地形或范围阻挡的点。几何节点连接附近网格和 1.5 单位内的其他间隙点，不生成额外的平移网格，从而覆盖完全落在固定网格线之间的窄缝。粗、细及几何节点共用同一节点表、二叉堆和 4096 次展开上限；直达仍优先，所有连接逐段验证。

历史基线：2026-10-08 的连续弯道夹具复现了“外侧进不去，放进入口后能走通”。当时旧实现先在外侧粗搜 2056 个节点，再从起点细搜耗尽剩余 2040 个节点，误判不可达；同一布局从入口出发只需粗搜 199 个节点。该轮局部细化修复（`f1d89d1`）从外侧用 1058 个节点完成路线并送入 7 个石头；该数据属于 0.7.5 修复基线，不是本轮 0.7.6 的重新测量。夹具使用合成墙体与原版 locomotor 方法，不代表截图坐标的精确复现或实机耗时。原版石墙除 .5 半径的实体碰撞外还注册 `Pathfinder:AddWall`；导航查询继续复制原有 `pathcaps` 并设置 `ignorewalls=true`，以真实圆形碰撞体检查这些墙，保留原版地形、水域与地图净空检查。不会修改 locomotor 自身的 `pathcaps` 或任何实体碰撞掩码；实体封路仍拒绝。

规划后用可通行射线平滑路径，自行维护当前转弯点；只在靠近该点且通向下一点的线段安全时推进。原版约 .7 单位的提前跳点不能覆盖此进度，`SetMoveDir` 在原版更新期间指向已验证的路径点；接近转弯点时限制 `SetMotorSpeed`，行走动画循环的 `WalkForward` 重新设速同样受限，避免冲过转角后回头。动作到达、状态机与交互仍由原版执行，不提交无范围约束的原版 `SubmitSearch`。

行驶复查在 .25 秒后进入按世界隔离的 FIFO 队列，每帧最多启动一份周期复查，可以跨帧完成；优先使用共享预算，但每帧最多占用 64 单位，给搜索保留机会。短暂排队时继续沿已验证路线行走；快照年龄从实体查询开始计算，达到 .5 秒、目标偏移超过 .25 单位，或进入原版动作到达距离时，停车等新快照。构建完成时已过期的快照也不能恢复行走。拿到新快照后验证目标位置、路线及移动进展，实际重规划仍停车；只有实际停车等待的时间不计入卡住，后台排队期间马达运转但没有进展仍视为物理卡住。取消或平台失效会丢弃排队任务。每帧检查当前路线段和自身范围，沿已验证直线行走时复用段检查，侧移、切换路径点或障碍快照变化后重新检查。路线被阻挡或连续 1.5 秒移动不足 .1 单位时重规划；非刷新时发现失效路线，先停车并等待允许的重规划时刻，避免每帧反复发起搜索。卡住最多重试两次后取消并暂避该目标。

末段接近点在目标实际移动后按当前目标位置重新计算，小于 .25 单位的位移也更新，避免停在旧终点等到卡住。较早的转弯点仍按已验证路线推进，静止目标保留原有接近点，尤其不破坏岸边切向接近。目标累计偏移超过 .25 单位或路线不再安全时，仍按上述规则重规划。

工作动画接触回调先执行语义 `ValidateAction`，再由 `Worker:CanInteract` 验证本次原版到达距离；此距离检查同时适用于两种寻路开关状态。新版导航还为该小车实例提供 `locomotor.ac_can_interact`，同步获取接触附近的新快照并复查静态遮挡和地图通行，不能复用到达后已由 `Stop` 清除的路线快照。这个局部同步检查不进入异步搜索预算。空间条件改变时仅失败一次、释放目标并允许重新选择，不施加失败冷却，不拆物品或消耗货物；角色不阻挡最后交互的原规则保持。行走中的语义巡检不要求已进入交互距离。

2026-10-06 的途中停顿检查在原版 locomotor、BrainManager 和 StateGraph 离线夹具中确认了两段等待：复查一进入队列就停车，随后原版 `OnLocomote` 将行走状态切成 `walk_stop`；复查完成时该状态既不是 moving 也不是 idle，无法响应恢复事件，仍需播完收步动画。现将短暂复查改为上述后台等待，并在 `walk_stop` 的更新回调中检查 `WantsToMoveForward()`，恢复后立即进入 `walk_start`。该修改只作用于本模组状态图，拾取、采摘及装箱的 busy 动画仍完整播放；待机扫描仍为 .5 秒，活动巡检仍为 .1 秒。

规划找不到路线或耗尽单次 4096 节点上限时，先按 .5 秒短退避，连续失败按 .5 / 1 / 2 / 4 / 8 秒递增，上限为 `retry_delay`（默认 10 秒）；成功或重新放置后清除失败次数。持续卡住、搜索超时和平台变化仍直接使用默认冷却。失败立即允许选择其他任务。返程 `WALKTO` 同样受避障约束，失败会通知原版监听器，独立 `nextreturn` 也递增退避至 `retry_delay`，成功或重新放置后清除次数，不阻塞工作扫描。平台上的搜索节点、目标、路径和进展均使用局部坐标，地图查询和行走路径随船平移/旋转；平台移除时停止搜索，船自身移动不冒充小车行走。该网格与净空判定偏保守，极窄通道可能判为不可达；真实物理与大量小车的服务器开销仍需实机验证。

车身移动与最后的交互接近分别验证。岸边视觉陆地可能由 Map 判为可通行，却不在原版 Pathfinder 的寻路地块内。2026-10-06 用户报告制图台旁岸边拾取后携带 1 个石头进入“运输受阻”；旧实现允许已经接近的岸边拾取，却要求随后离开当前位置的每条行车线段都通过原版射线，导致起点落在延伸区域时所有候选路线被拒绝。离线场景使用原版制图台的 .4 碰撞半径，在移动夹具及原版 locomotor 下复现了该缺口；截图的实际地形与物理仍待用户复测。

`TerrainClear` 仍优先执行原版射线。仅在射线被拒绝、两个端点均可通行且至少一个端点由 `Map:IsPassableAtPoint(..., false, true)` 的第二个返回值标为岸边延伸区域时，启用局部回退：整段按不超过 .1 单位的间隔采样中心和车身左右净空，真实水域立即拒绝；每段连续的非延伸陆地仍须通过原版射线，避免以岸边起点绕过无关的陆地寻路限制。实体碰撞和工作范围检查在该回退前执行。检测到延伸区域时允许上述细网格重试，沿岸绕行、拾取后离开和空载返程共用规则；不会改动原版 Map、Pathfinder 或物理碰撞。

`InteractionClear` 不要求寻路射线抵达物品中心，而是沿接近线每 .1 单位检查 Map 可通行性，并检查静态实体的真实碰撞半径。排除目标自身的碰撞体以允许正常靠近箱子；玩家和生物仍参与行车避障，但不阻挡最后的交互接近，避免丢物品的玩家站在原地时将目标判为不可达。岸边物品可在原版动作距离内从陆地侧拾取，隔水或穿过静态实体的接近线仍拒绝。若直线距离已满足原版到达判断但接近线受阻，暂缓该判断并继续沿安全路径行走，防止只凭距离提前执行。

路径点按原版 `{ x, y, z }` 坐标契约处理，转向和平台坐标转换不调用路径点的 `Get()`。A* 节点已经位于交互距离内时，将其转换为独立坐标，避免把没有 Vector3 方法、且含搜索父节点的表直接交给移动层。该分支曾在用户实机中触发 `ac_navigation.lua:320: attempt to call method 'Get' (a nil value)`；Insight 仅转报服务器错误，当前实现与离线回归已修正此问题。

目标占用用于避免多机重复选择同一资源。普通失败目标暂避 10 秒，纯规划失败先采用上述短退避；任务超时为 20 秒。暂停、捡起、重新放置和休眠走取消与清理流程。选择目标和接触时均检查实体有效性、工作状态及可交互条件。

v0.5.4 将 watchdog 的途中复查从装箱扩展至所有任务；v0.5.5 在存在 `pending` 任务时每 .1 秒调用 `ValidateAction`，覆盖行走及交互接触前。当前任务成功、失败或取消后撤销高频定时任务，恢复 .5 秒待机巡检，并主动调用原版 `ForceUpdate()` 唤醒可工作的 Brain；组件移除时取消当前定时任务。待机 `GetNextAction` 以 .5 秒节流，Brain 优先级每 .1 秒重评并关闭启动随机等待；放置、重新启用和成功完成任务时清除 `nextscan`，仍由 busy 状态等待当前动作动画结束。工作和返程使用独立 `DoAction`，新工作可以抢占返程，有效工作继续完成。`FindPath` 选定目标后进入上述共享队列，剩余预算足够的简单路线可当帧完成，复杂路线分帧计算；不等待原版异步搜索。此前同步搜索版本的 .5 秒放置等待、.5 秒扫描节流和 .25 秒 Brain 重评可解释短延迟，不能解释实机约 10 秒的等待。正常 BrainManager 与 StateGraph 待机测试未复现该长延迟，人为设置 10 秒睡眠或 Hibernate 只验证主动唤醒；该阶段尚未确认实机根因。

2026-10-06 用户报告：应用 0.6.2.1 的全局 `bit` 启动修复，并关闭客户端模组 `DontStarveLuaJit2` 与“无卡顿加载”后，未再观察到待机长等待。上述测试组合的响应恢复正常；因多个条件同时变化，尚不能将长等待归因于其中某一个模组或启动修复。保留当前调度与默认关闭的诊断，不因这次反馈继续修改扫描间隔。

活动巡检仅验证当前任务，不扫描全部工作目标或抢占更优目标；拾取及普通资源验证可能查询匹配容器列表和实际容量，同一时刻继续复用容器列表缓存，因此不是纯常数开销。物品被其他实体拾取、移除或移出安全范围，植株被抢采，巨大果实被敲开，以及真实接收条件变化时，巡检先发现失效时通过 `Cancel(true)` 通知原版 `DoAction` 的失败监听器、释放目标占用、清理 locomotor 与 BufferedAction、恢复 idle 并将下一次扫描时间归零。v0.5.6 同时覆盖原版 locomotor 在巡检前触发失败的路径：`Finish` 在任务释放前验证世界条件，识别失效后免除冷却并解除扫描等待，不在尚未清空失败监听器的回调内再次同步失败或清理动作。实际 `PerformBufferedAction` 执行期间的回调失败仍按普通失败处理，避免把自产物造成的库存变化误判为外部失效；暂停和超时也保留原规则。返回中心的 `WALKTO` 不建立 `pending`，不启用高频巡检。此类世界状态变化不惩罚目标冷却，未成功采摘不增加计数，已有运输货物保持原实体和数量。

可选 `SetDebugEnabled(true)` 诊断默认关闭且不存档。记录扫描（最多每秒一次）、任务选择、路径结果和动作结束；调试状态包含状态机、BrainManager 队列、扫描间隔、返程标志、冷却数量、重试剩余时间及最近失败原因。用于区分实际调度等待与目标冷却，不改变物品和交互规则。

取消与未完成动作的状态退出统一走 `FailAction`，调用原版动作失败回调后释放组件任务，避免只清掉 `pending` 而使 Brain 中的 DoAction 留在 RUNNING。超时和普通工作失败仍保留原有冷却。

## 动作时序与关箱生命周期

普通拾荒机只执行下表的拾取和装箱；采集车额外执行采摘、收获与敲巨大作物。内置套件将移速从 3 提升至 6，所有作业时间保持不变。扩展的动作速度接口仍会同步改变播放、接触与结束时刻。

| 状态 | 动画 | 总时长 | 接触时刻 |
| --- | --- | --- | --- |
| 拾取 | `pickup` | 1 秒 | .5 秒 |
| 采摘 / 收获 | `hammer` | 1.3 秒 | .7 秒 |
| 敲巨大作物 | `hammer` | 1.3 秒 | .7 秒 |
| 装箱 | `store` | 1 秒 | 第 6 帧，.2 秒 |

拾取只为本模组的 BufferedAction 设置 `1` 世界单位的到达距离，与原版 `winona_storage_robot.PICKUP_ARRIVE_DIST` 一致；原先的 `.15` 小于两车同点作业时可同时达到的距离，容易使两车在进入拾取状态前互相挤住。靠近目标即可进入动画并在接触时复查、执行原版 `PICKUP`，不修改全局动作或移除碰撞。保留拾荒机原有下沉动画和 .5 秒交互时刻，不复制薇机人的前冲运动。冲撞和下沉只改变动画图层，实际位移由原版 locomotor 完成。状态进入时面向目标，四面朝向由引擎结合镜头选择，支持 Q/E 转动。

装箱参考原版 `SGstorage_robot`：第 6 帧执行原版 `STORE`，由原版动作打开容器；成功回调释放任务，但保持箱子开启到装箱状态退出。小车默认动画长 1 秒，故开启持续约 .8 秒；原版动画总长度不同，未强制延长小车动画。

v0.4.2 同步将绑定接触帧和点头曲线峰值提前至第 6 帧；状态机交互、动画姿势与加速倍率保持一致。此前只提前动作而没有更新动画的问题已修复。

任务完成后状态仍带 `busy`，Brain 不启动下一次作业。失败、非动画存放及时关箱；正常完成、暂停或其他状态中断由退出回调清理。关闭的是小车自身的容器开启关系，保留其他开启者。动作只能在接触时执行一次，失败不会直接改变货物数量。

## 美术、兼容与扩展

模型只包含三张原创车身贴图及贴图自带的车轮，没有夹子、盖子、独立轮子或货包。三视图导出 21 段动画、585 帧，每帧一个车身元素；侧面掩码 `5` 由引擎镜像，避免重复左侧动画。绑定、曲线和编译格式见 [美术说明](ART.md)。

背包贴图使用 64×64 画布，车身限制在 48×48 内容区域；生成独立库存预览并通过官方纹理转换器编译。该调整不缩小世界中的实体或小地图图标。

标准 `inventoryitem`、`pickable`、`crop` 与 `container` 通常可复用；角色专属字段、定制采摘回调、未知产物与非标准容器需适配并测试，不能保证所有第三方组合兼容。实体标签 `ac_ignore` 排除采集，`ac_no_delivery` 排除卸货，`ac_delivery_container` 允许符合安全条件的其他容器类型。

适配器名称由 `ac_api.RegisterAdapter` 在新增注册时排序，同名注册只替换处理器。`ac_targets.Kind` 复用 `GetAdapterNames()` 的共享只读列表，不再为每个未命中内置规则的候选创建、填充并排序名称表。名称升序、标准规则优先与后续注册生效保持原行为；适配器自身的匹配查询仍按候选逐一执行。

v0.5.0 接入棱镜与勋章的只读产物元数据。v0.5.1 根据游戏反馈取消农作物产量与接收预检，改用上述 5 个一批流程；雨竹等普通资源继续使用只读元数据。每次交互调用原版 `PICK` / `HARVEST`，由植物自己的回调生成真实产物并重生、保留垄，不使用挖掘或破坏接口。第三方角色专属回调及后续接口变化仍需实机验证。

Insight 在所有模组完成加载后的 `AddSimPostInit` 通过 API V1 注册，兼容其低加载优先级。服务端提供状态、农作物批次阶段与计数、半径、货物与运输规则信息，客户端只读取同步的工作中心、平台与半径；范围圈挂在独立临时锚点上，以放置点为中心，船上使用平台局部坐标并随船更新。范围更新不扫描采集目标，不启动服务端作业，取消悬停和实体移除时清理。

0.6.0 通过 `ac_upgrades` 注册单级 `ac_chassis_mk2`，套件配方为铥矿 ×10 / 废铁 ×3 / 月岩 ×5，炼金引擎解锁。`AC_UPGRADE` 使用 USEITEM 右键及玩家短动作，优先级 3；鼠标持套件时抑制优先级 2 的采集切换候选，已升级目标保留失败提示。安装先复查目标、玩家与所有权，再同步取消旧任务、从原版库存分出单件、设置等级及消费；锁阻止重入，异常恢复等级、速度与套件。升级取消不添加目标冷却，释放占用并关闭小车自己的箱子开启关系，保留采集偏好、扩展完整启停、真实货物、工作中心与农作物批次。成功使用 .4 秒无交互点头反馈。

拾荒机与采集车现分别注册 `automatic_collector` 和 `automatic_collector_mk2`，共用原 prefab 文件中的实体工厂；直接生成采集车时默认应用底盘等级 1。升级与撤销通过原版 `SetPrefabName` 修改原实体的 Lua / 引擎名称，存档由原版 `GetSaveRecord` 记录对应代码，保留实体、货物及工作状态。旧的 `automatic_collector` 存档仍按已保存等级恢复采集车，并在下次保存时写入新代码。两款车继续共用 `automatic_collector` 标签，动作、目标排除和避障识别均保持；采集车补齐检查描述，Insight 为两个 prefab 分别注册范围提示。

`_ac_mk2` 在 SetPristine 前声明，dirty 及初始刷新同步 prefab 名称并切换独立 bank / build、地图图标与默认名称。0.7.4 移除固定的显示名回调，沿用原版 `GetBasicDisplayName` 的名称回调、覆盖名、作者过滤和实体名称优先级。刷新时只将原 prefab 的默认名称改为当前等级的默认名称；保留其他名称、原版 `named` 非空网络字段的名称，以及未使用 `named` 时带作者信息的名称，包括恰好等于默认名称的命名。原版 `named` 清除名称后可能仍保留实体的旧作者字段，此时以空名称网络字段判断已清除，允许更新默认名称，过滤仍交给原版方法。

2026-10-08 首次修复在客户端构造后增加 `DoStaticTaskInTime(0, Upgrades.RefreshVisual)`，覆盖网络初始反序列化没有 dirty 事件的路径。用户随后确认旧存档与新安装套件的车在再次读档后外观变成普通车，但服务端行为似乎保留，升级套件仍拒绝安装，且可被 `c_removeall("automatic_collector_mk2")` 删除。检查发现 mk2 构造时仅服务端在 `SetPristine` 前把 `_ac_mk2` 设为 true，客户端保留 false；初始同步若不重新下发未变化的字段，延迟刷新会继续使用 false，并将已由 AnimState 同步的高级外观刷回普通车。

当前两端均按 prefab 入口设置相同的 `_ac_mk2` 初值后再调用 `SetPristine`，保留静态复查和后续 dirty 监听。服务端等级、存档格式及货物未改变；旧存档的普通代码名仍由 `ac_upgradable` 恢复等级后迁移为 mk2，新保存的 mk2 构造初值在两端一致。新增夹具记录 pristine 初值并省略未变化字段，延后服务端加载任务，覆盖旧存档迁移、实际套件升级、直接生成 mk2 及普通车的连续三次保存/恢复。修复前 12 个 mk2 场景失败、4 个普通车场景通过；这说明旧夹具每次强制提供 mk2 网络值遗漏了默认值路径，尚不等同于实机网络协议验证。

库存 atlas 和 image 由原版组件同步。新建实例使用 .25 半径的角色碰撞体，等级刷新同时调用原版 `Physics:SetCapsule(.25, 1)`：拾荒机与采集车半径均为 .25（直径 .5），胶囊高度参数为 1；原版质量、碰撞组、掩码和美术缩放保持。服务器安装与读档、客户端 dirty 与晚加入均应用尺寸，撤销等级或安装失败回滚也保持此尺寸；导航直接使用当前 Physics 半径并额外保留 .05 净空。等级由已有 `ac_upgradable` 保存，延迟读档幂等应用；只有行走前摇、循环、收尾使用 2 倍播放，退出行走恢复 1。保留移动速度、动作速度、Light、等级持久化与 `1..8` 运输槽扩展接口。降低容量不得截断已有货物；未知升级等级保留以便扩展恢复。适配器提供纯查询的匹配、动作与主产物描述，详情及示例见 [扩展接口](API.md)。

`DeliveryCapacity` 查询的是同一组货物可送入的单个箱子的最大容量，不累加多个箱子容量。0.7.4 在合格箱子的可接收量达到 `maxcount` 后立即返回；不足时继续遍历，样品匹配、容器过滤、冷却和实际物品/皮肤检查保持原规则。接收箱偏好仍由 `FindContainer` 完整比较，接触时继续复查真实容量。100 箱均足够接收的离线场景将单次容量查询由 100 次降至 1 次；这是调用次数验证，实际服务器负载仍需实测。

旧版世界升级至新代码可正常迁移；0.7.3 及以后保存的采集车记录不能由未注册 `automatic_collector_mk2` 的 0.7.2 或更早版本加载。回退模组需恢复升级前备份。
